# 全流程详解：用卫片核查已提取的车道中心线

本文档逐环节说明 `merge_split2` 的完整管线，重点是**送给大模型的输入到底是什么**、
**它必须吐回什么格式**，以及每一环为什么这样设计。

---

## 0. 一句话概括

不从整幅影像里"找问题"，而是**先用纯矢量拓扑把可疑点收缩到 40 个**，
每个点裁一张 138 m 见方、沿道路走向旋转过的原生分辨率小图，
把矢量渲染上去，让大模型对每条车道做**六选一的选择题**并给出改法。

整幅图 → 40 张有具体问题的小图。调用量降一个数量级，每题也变简单了。

---

## 1. 输入数据与坐标系

| 项 | 值 |
|---|---|
| 卫片 | `merged.tif`，10752 × 11776 px，RGB，无压缩 TIFF |
| 几何参考 | ModelTiepoint (0,0)→(5740726.57, 2895167.10)，ModelPixelScale 0.14929 |
| 投影 | EPSG:3857 |
| 纬度 | 25.1507°N |
| **地面分辨率** | **PS × cos(lat) = 0.13514 m/px** |
| 影像覆盖 | 约 1.45 km × 1.59 km |

**坐标系有个坑**：0.14929 是 3857 投影单位/像素，不是地面米。所有"米"的度量必须乘
`cos(lat)`。搞错这一项会让所有距离判据偏大 10.5%。

内部统一用 **图像像素坐标 (px, py)**，原点左上，`py` 向下：

```
px = (x - X0) / PS
py = (Y0 - y) / PS
```

矢量图层：

| 图层 | 条数 | 用途 |
|---|---|---|
| `Lane.geojson` | 548 | 被核查对象 |
| `LaneBoundary.geojson` | 364 | 判断"该断还是该续"的旁证 |
| `Curb.geojson` | 185 | 同上 |

Lane 的属性里 `Width` 全是 3.5，`IsLeftmost`/`IsRightmost` 全 true，
所以**不能靠属性判断车道左右关系**，只能靠几何。

Lane 几何极简：中位数 3 个顶点，197 条是纯两点直线。分合流的曲线细节不在 Lane 里。

## 2. 阶段 A：候选点生成（`candidates.py`）

**这一步完全不看影像**，只用矢量 + 一点栅格元数据（判黑块）。

### 2.1 为什么改掉"找断头点"的思路

原始想法是找"断头点"。实测：

> 548 条 Lane 的 1096 个端点，在 **2 m 容差下 deg0 = 0** —— 没有一个游离端点。

按"断头"去找，一条也找不到。真正的判据是**节点度数**。

### 2.2 建图

1. 把全部 **2118 个顶点**（1096 个端点 + 1022 个内部顶点）按 **1.0 m** 半径聚类成 **1326 个节点**（并查集）
2. 每条 Lane 首末顶点映射到节点，建立"节点 ↔ Lane"的对应
3. 统计每个节点的**线端数** `deg`：一条线的端点落在这里记 1，只是穿过这里记 2

得到 1326 个节点，其中 **deg ≥ 3 的只有 15 个**。

> **为什么用全部顶点而不是只用端点**：为了处理 **T 型接合**
> ——一条线的端点撞在另一条线的中间顶点上。只用端点建图，这种连接完全看不见。
>
> 早期版本在这里有个盲区：`lanes_at` 只按端点填充，导致 54 个含 T 型接合的节点里
> 有 4 个丢失了连接关系；另有 40 个 T 型节点因为"端点间邻接"算出来 deg=2 而被判成没问题。
> 现在的做法是**所有顶点都参与建节点集合**，`deg` 改为线端数，这些节点正确得到 deg=3。
> 修复前后候选数都是 40，但 3 个原判 `seam+dangle` 的点升级为 `branch+seam+dangle`。

### 2.3 三条判据

| 理由 | 条件 | 含义 |
|---|---|---|
| `branch` | 节点度 ≥ 3 | 多条 Lane 汇聚/分开 |
| `dangle` | 节点度 ≤ 1 | 悬空末端（"断头"的正确形式） |
| `seam` | 不同 RoadId 交接，且接缝不自然 | 见下 |

`seam` 的具体条件（三者满足其一）：

- 接缝两侧 **车道数不等**
- 最差 **折角 > 18°**（用端点处 30 px 内的走向向量算，理想对接时点积 ≈ −1）
- **横向错位 > 1.5 m**

> 399 个不同 RoadId 交接的节点里，只有 16 个真正不自然。其余都是正常的分段拼接
> —— 如果不过滤，光这一类就产生几百个候选，直接淹没真正的信号。

### 2.4 合并

同一处问题常常"每条车道各报一次"（3 条车道一起断头 → 3 个 dangle 节点）。
用 **45 m 半径**空间聚类，把同一条事件合并成一个候选，中心取加权平均（branch 权重 3、其余 1）。

再丢掉：离影像边缘 < 40 px 的、落在黑块（无影像覆盖）上的（平均亮度 < 12）。

### 2.5 结果

**40 个候选**：`branch` 11、`seam` 10、`dangle` 38（可重叠）。

排序优先级：`branch+seam` > `branch` > `seam` > `dangle`，同级按涉及车道数降序。

一个候选长这样：

```json
{"x": 3428.47, "y": 5781.43,
 "reasons": ["branch", "dangle"], "kind": "branch+dangle",
 "deg": 3, "n_nodes": 5,
 "lanes": [67150, 67376, 67377, 67378, 67455, 67456, 67457],
 "roads": [67004, 67049, 67071],
 "lane_counts": [1, 3],
 "note": "", "cid": "C0009_0016"}
```

## 3. 阶段 B：渲染（`render.py`）—— **决定了模型能看到什么**

这是整条管线里最影响成败的一环。渲染错了，模型再强也答不对。

### 3.1 裁剪参数

| 参数 | 值 | 理由 |
|---|---|---|
| 图幅 | 1024 × 1024 px | = **138.4 m** 见方 |
| 分辨率 | 原生，不重采样 | 车道虚线在 1024 下清晰可辨；512 m 瓦片下糊成一片 |
| 旋转 | 沿候选处主导走向 | 道路接近竖直，模型读拓扑更容易 |
| 中心 | 候选点 | 固定在画面正中 |

"主导走向"的算法：取候选点 40 px 内所有 Lane，各自算端点走向向量（30 px 跨度），
求和后归一化，再转成旋转角。

### 3.2 图层样式

| 图层 | 颜色 | 线宽（原生 px） | 换算 |
|---|---|---|---|
| **待核实 Lane** | 红 `(255,45,45)` | **5** + 4 px 半透明晕 | **≈0.68 m + 0.54 m 晕** |
| 周边 Lane | 灰 `(150,150,160)` | 3，alpha 130 | ≈0.41 m |
| 端点 | 白方块 10×10 | 2 px 白边 | — |
| 候选点 | 黄十字 + 圆环 | 3 px | — |
| Lane 编号 | 黄底黑字 `L243` | — | 与右侧结论文本对应 |
| 标签引线 | **黄色短虚线**（9 px 实 / 7 px 空） | 2 px | 刻意区别于车道线 |

两个细节是踩过坑才定下来的：

1. **引线必须用黄色虚线**。最初用红线画引线，模型把它当成了车道线，
   在 evidence 里描述"一条斜出的支线"——其实是标注。
2. **编号标签要避让**。密集区几十条并排车道，标签会糊成一团，
   模型会读成 `L2810`（L28 和 L10 粘在一起）。现在的做法是标签排到图幅两侧空白区
   （命令行版）或用占位避让推出去（查看器版），同一条车道只标一次。

### 3.3 关键：**两张图**

每个候选输出两张：

| 文件 | 内容 | 典型体积 |
|---|---|---|
| `sat.png` | 卫星影像 + 矢量叠加 + 标签 | ~1.3 MB |
| `vec.png` | 同视角纯矢量，黑底，无影像 | ~28 KB |

**为什么要两张**：让模型分离"我看到的路面"和"你提的矢量是什么"。
只给叠加图时，模型容易把红色标注线本身当成待评价对象；
给了纯矢量图，它可以先理解拓扑（哪条线在哪断开、怎么接的），再看影像核对。

`sat.png` 里是**烧入式**标注——文字标签、引线、白方块都已经画进像素。
（交互式查看器 `viewer/` 用的是另一套**干净底图**，标记全部客户端 SVG 叠加。）

### 3.4 每张图的元数据

`meta.json` 记录：`crop_px`、`ground_m`、`rotation_deg`、高亮车道列表
（`k` 全局下标、`id`、`road`、`len_m`、锚点、标签位置）。
其中 `crop_px` 和 `ground_m` 会填进 prompt 的 `{size}` / `{meters}` 占位符。

## 4. 阶段 C：模型调用（`ask.py`）—— **核心**

### 4.1 请求构造

```python
p = {"model": "claude-fable-5-2",
     "max_tokens": 16000,
     "thinking": {"type": "enabled", "budget_tokens": 8000},
     "messages": [{"role": "user", "content": [
         # ① 图像 1：卫星 + 矢量叠加
         {"type": "image", "source": {"type": "base64",
                                      "media_type": "image/png", "data": <sat.png>}},
         # ② 图像 2：纯矢量
         {"type": "image", "source": {"type": "base64",
                                      "media_type": "image/png", "data": <vec.png>}},
         # ③ 文本 prompt
         {"type": "text", "text": PROMPT}]}]}
```

- 图像顺序固定：**先卫星图，后纯矢量图**，prompt 里也是按这个顺序描述的
- 图像以 base64 PNG 内联，不传 URL
- 开 thinking，预算 8000 token
- 单次超时 900 s；对 429/5xx 做 5 次指数退避（20/40/60/80 s）

### 4.2 Prompt 原文

> 第一张图是正射卫星影像（图上红线是我们已有的车道中心线矢量，黄色十字是待核对的位置）。
> 第二张图是同一视角的纯矢量图：红色=待核实的车道中心线，灰色=周边已有车道中心线，
> 白色小方块=每条线的端点（也是矢量断开或相接的地方）。图幅 {size} 像素约 {meters} 米见方，
> 已旋转使主要道路接近竖直，上不作方向参考。
>
> 注意图上的标注：黄色十字=待核对位置；黄色短虚线+黄色框+L 编号=仅仅是标签引线，
> **不是**车道线，不要把它当成路面结构。
>
> 我们的目标：核对【红色矢量】是否与影像上的真实车道一致，重点看黄十字附近的端点和分合流处。
>
> 请逐一检查红色中心线（L 编号标在线上），判断下列哪一类问题（可多选，若无问题就是 ok）：
>
> - **A. missing_lane（该续未续）**：影像上这条车道明明继续延伸，矢量却在此断开了。
> - **B. wrong_break（本该断开却连上了）**：影像上这里车道终止/车道线不存在
>   （例如撞上导流区、路肩尽头、被中央分隔带/护栏截断），矢量却在这里结尾或拐进了不该进的地方。
> - **C. wrong_branch（分支/合流错误）**：影像上的分/合流形态与矢量不符——例如应有分叉却没有、
>   不该分叉却分叉了、合流方向接反、有车道在分合流处"穿越"了导流区。
> - **D. wrong_count（车道数不符）**：穿过某个断面的车道数与影像上的行车车道数不一致
>   （多一条或少一条）。
> - **E. ok（就这一段没问题）**：端点/连接是合理的，影像与矢量一致。
> - **F. unreadable**：影像在此处看不清（云、阴影、无影像黑块、车辆遮挡）。
>
> 判断要点：
> - 看路面本身：车道分隔线（虚线/实线）、导流区人字形斜纹、车道线起止的尖端 (nose)、
>   实线变虚线的位置。
> - 端点落在导流区里、压着斜纹区、或跨过实体分隔带 → 偏向 B。
> - 端点附近影像上车行道仍在延续、只是我们的线停了 → 偏向 A。
> - 一条线在分合流处穿过斜纹区/直接横切 → 偏向 C。
> - 不要因为"两条线之间有空隙"就判 A：同向车道本来就是并行的，空隙是正常的车道间距。
>
> 请只输出一个 JSON，不要其他文字：
> ```json
> {"verdicts": [
>    {"lane": "L12",
>     "problem": "missing_lane|wrong_break|wrong_branch|wrong_count|ok|unreadable",
>     "confidence": 0.0~1.0,
>     "where": [x, y],
>     "evidence": "一句话看什么判断的",
>     "fix": "一句话该怎么改"}
>  ],
>  "overall": "一句话总结这一处的主要问题",
>  "severity": "high|medium|low|none"}
> ```

### 4.3 Prompt 设计上的几个决定

**为什么是"六选一"而不是自由描述**：
自由描述无法聚合、无法和标注对比、也无法追问"哪几条车道错了"。固定枚举让输出可解析、可统计。

**为什么要加 `wrong_break`（第 4 类）**：
原始需求只列了三类（分支合流错 / 该续未续 / 本来就该断）。
`wrong_break` 是"连了但不该连"——端点在拓扑上是接上的，所以**只看断头点永远发现不了**。
但合流处穿进导流区正是最常见的错误形态。

**为什么显式声明"空隙不算 A"**：
不加这条，模型会把并排车道之间的正常间距判成"漏了一条车道"，`missing_lane` 会泛滥。

**为什么要求 `evidence` 和 `fix`**：
- `evidence` 让判断可核对——人可以看出它是真看了影像还是在猜
- `fix` 把"哪里错"变成"怎么改"，直接可用于生成修正建议

**为什么允许 `ok` 和 `unreadable`**：
没有负例选项，模型会倾向于报告问题（倾向性偏差）。给 `ok` 一个正当出口很关键。

| 字段 | 类型 | 含义 | 可靠性 |

| `problem` | 枚举 6 值 | 问题类型 | 主输出，相对稳定 |

| `fix` | 字符串 | 一句话改法 | 可转成 `extend`/`relink` 等动作 |
| `overall` | 字符串 | 该处总评 | — |
| `severity` | 枚举 4 值 | 该处严重度 | — |

| 指标 | 值 |
|---|---|
| 调用次数（2 轮 × 40） | 80 |
| 平均输入 token | 4299 |
| 平均输出 token | 5902 |
| 其中 thinking 占比 | **89%** |
| 平均延迟 | 54 s（中位 47 s，最大 141 s） |

prompt 本身约 1200 token。输出 5900 token 里 89% 是思考过程。

## 5. 阶段 D：后处理与落地

### 5.1 解析（`ask.py::parse`）

容错顺序：先找 ` ```json ``` ` 代码块（从后往前），再退化到"第一个 `{` 到最后一个 `}`"。
解析失败不丢记录，保留 `raw` 字段。

### 5.2 锚定（`webexport.py`）

`where` 坐标不可靠，所以做一步**锚定**：把结论点投到它所指车道上的最近点。

```python
anchor, dev_px = nearest_point_on_lane(lane.pts, where)
dev_m = dev_px * 0.13514
```

86 条"有问题"的结论里，**83 条成功锚定**；剩下 4 条是模型没写编号或写错。

实测偏差分布：**p50 = 6.6 m，p90 = 26.6 m，最大 41 m**。

> 结论：图上的圈位置要"锚定到车道"才有意义。模型自报坐标只能当粗提示。

### 5.3 转成可执行建议（`review.py::apply`）

| verdict | action |
|---|---|
| `missing_lane` | `extend` |
| `wrong_break` | `trim_or_relink` |
| `wrong_branch` | `relink` |
| `wrong_count` | `recount` |

过滤 `confidence < 0.4` 的。最终 **85 条建议、涉及 80 条不同 Lane**：
`extend` 67 / `relink` 13 / `recount` 3 / `trim_or_relink` 2。

### 5.4 一致性（`review.py::cross_check`）

同一条 Lane 被多个候选重复指出 → 信号远强于模型自述的 confidence。
输出 `consensus_*.json`。

## 6. 可靠性：必须知道的三个数字

### 6.1 单次结果不稳定

| 对比 | 候选级 lane 集合一致 | 共同 lane 上类型一致 |
|---|---|---|
| **同图跑两次**（纯采样随机） | **18/40** | 53/63 |
| 换一版渲染前后 r1 | 17/40 | 31/54 |
| 换一版渲染前后 r2 | 18/40 | 39/62 |

**换渲染的差异 ≈ 纯采样差异。** 也就是说单次调用里"哪个 lane 有问题"约 55% 会变。

→ 单次结果**不能**当标签用。**两轮都指出的 53 条 lane 级结论**才可靠。

### 6.2 置信度不可信

模型给 0.4–0.7 密集分布，但这与实际正确率**不相关**。
更可靠的排序信号是"被几个候选重复指出"。

### 6.3 没有真值

目前**没有任何人工标注**，所以无法计算 precision / recall。
任何"准确率 xx%"的说法都是编的。

唯一的评测途径是构建标注集：从 53 条稳定结论里抽查一部分人工确认，
再加上"本来就该断"的负例。

`viewer/` 里的 `✓ 对 / ✗ 错` 按钮就是为此设计的，导出写入 `annotations.json`。

## 7. 已知局限

1. **视野只有 138 m**，约 4 秒车程。跨图幅的长距离漏提看不出来——
   如果一条线该延伸 200 m，本方案只告诉你"这里断了"，不给完整走向。
2. **`dangle` 候选有噪声**：路段拼接、规划中的路口都会产生悬空端点。
3. **模型标签偶有错写**（L3→L13、不写编号），导致约 5% 的结论无法锚定。
4. **只支持单幅卫片**；多幅拼图需要先做影像镶嵌。
5. **`ok` 判定同样不稳定**——所以"某处没问题"这个结论尤其不能直接采信。
