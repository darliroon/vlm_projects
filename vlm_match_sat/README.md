# vlm_match_sat — 用卫片核查已提取的车道中心线

目标：给定卫片 + 已提取的 `Lane.geojson`，找出**提取结果与影像不符的地方**，重点在分支/合流和断头处。

## 一句话结论

不要"盲切瓦片让模型找问题"。先用**矢量拓扑**把可疑点收缩到 40 个，
每个点裁一张原生分辨率小图（矢量渲染上去），再让模型只回答**选择题 + 给修法**。
调用量从 400+ 瓦片降到 40 张，且每张都在问一个具体问题。

## 为什么改了原来的想法

| 原想法 | 实测结果 | 改成 |
|---|---|---|
| 找"断头点" | 这份数据 1096 个端点 2 m 内全有邻居，548 条 Lane 无游离端点 | 找**度数**：度≥3 是分合流，度=1 是悬空末端 |
| 512 m 瓦片 | 约 150 m/瓦片才看得清标线，512 m 下虚线糊成一片 | 原生分辨率，1024 px ≈ 138 m |
| 让模型画框 | 框回归误差大，且没有"改什么"的信息 | 让模型输出 **verdict + evidence + fix** |
| 统一视角 | 道路横向时模型读错走向 | 每个 crop **沿车道走向旋转**成竖直 |

## 管线

```
candidates.py  →  candidates.json      纯矢量拓扑，40 个可疑点
render.py      →  ret/<ver>/crops/Cnnn/{sat,vec,meta}.png   卫星图+矢量 / 纯矢量图
ask.py         →  ret/<ver>/works/<model>/s<size>_<tag>/r<rep>/Cnnn.json   模型判断
review.py      →  ret/<ver>/sheet_*.png（人眼核查台）+ proposals_*.json（可执行的修改建议）
```

### 1. 候选点生成（`candidates.py`）

先把全部 **2118 个顶点**（含内部顶点）按 1 m 聚类成 **1326 个节点**，再给每个节点打理由：

- `branch`：节点**线端数** ≥ 3，多条 Lane 在此汇聚/分开
- `dangle`：线端数 ≤ 1，端点只连着自己——**这才是"断头点"的正确形式**
- `seam`：不同 RoadId 交接且不自然（车道数不等 / 折角 >18° / 错位 >1.5 m）

> 用全部顶点而非只用端点，是为了看见 **T 型接合**（一条线的端点撞在另一条线的中间顶点上）。
> 只用端点会把这种三条路的交汇误判成"一条路的内部拐弯"。

399 个不同 RoadId 交接的节点里，只有 16 个真正不自然；其余是正常的分段拼接。

然后用 45 m 半径把同一个路口的多条理由合并成一个候选（3 条车道一起断头 → 1 个候选），
按 `branch+seam > branch > seam > dangle` 排序。

**cid 是几何稳定标识**（如 `C0009_0016`，取 50 m 网格坐标），不由排序决定。
因为 `crops/` 和 `works/` 里的文件都按 cid 命名，cid 一旦漂移，图和结果就会错位——
这个坑踩过一次（换判据后 12/40 的编号变了）。

结果：40 个候选（branch 11、seam 10、dangle 38，可重叠）。

### 2. 渲染（`render.py`）

- 原生分辨率 1024 px（≈138 m），不重采样，虚线/导流斜纹清晰
- 沿候选处车道走向旋转，道路接近竖直
- 相关 Lane 红色高亮 + 编号 `L0..Ln`；周边 Lane 灰色淡化作上下文
- 标签排到图幅两侧空白栏，用引线指向车道（避免并排车道标签粘成 `L2810`）
- 每条线的**端点画白色小方块**——这是模型判断"断在哪、接得对不对"的主要线索
- 同时给一张纯矢量图 `vec.png`，让模型分离"我看到的路面"和"你提的矢量"

### 3. 模型判断（`ask.py`）

模型输出结构化结论而非坐标框：

```json
{"verdicts": [{"lane": "L12", "problem": "missing_lane",
               "confidence": 0.7, "where": [x, y],
               "evidence": "斜纹区尖端在线上方 3 车道处，线穿过了斜纹",
               "fix": "向南延长约 40 m 到车道线消失处"}],
 "overall": "...", "severity": "high|medium|low|none"}
```

六类判定对齐你的三类问题：

| 你的分类 | 本方案 |
|---|---|
| 一、分支合流错误 | `wrong_branch`（形态不符/穿越导流区）、`wrong_count`（车道数不符） |
| 二、直线断裂/漏提 | `missing_lane`（该续未续） |
| 三、本来就该断 | `ok`（端点落在导流区/路肩尽头是合理的） |

额外加了 `wrong_break`：**矢量连了但不该连**（穿进导流区、压在实体分隔带上）。
这一类比"该续未续"更容易被漏掉，因为你只看断头点永远找不到它。

### 4. 核查与落地（`review.py`）

- `sheet` 生成联系表：每个候选一张缩略图，把模型说的位置画成圆圈，人一眼判断对错
- `apply` 把 `fix` 转成 lane 级建议：`extend` / `trim_or_relink` / `relink` / `recount`

## 结果（claude-fable-5-2, 1024 px, 40 个候选，独立跑 2 次）

单次运行约 53–65 s/候选，输出 150 条 lane 级判断，其中约 85 条判为有问题。

**两次独立运行的一致性（关键数字）**

| 对比 | 候选级 lane 集合一致 | 共同 lane 上类型一致 |
|---|---|---|
| 同一张图 r1 vs r2（纯采样随机） | 18/40 | 53/63 |
| r1 vs 换了渲染的第一版 | 17/40 | 31/54 |
| r2 vs 换了渲染的第一版 | 18/40 | 39/62 |

**结论：更换渲染带来的差异 ≈ 纯采样随机性带来的差异。** 也就是说单次调用给出的
"哪个 lane 有问题"有 ~55% 会变。所以：

- 单次结果**不能**当标签用；
- **两次都指出的 53 条 lane 级结论**才算可靠信号（`consensus_*.json`）；
- 报告准确率必须先建标注集，现在没有真值，任何"准确率"说法都是假的。

**问题类型分布**（r2，151 条 lane 判断）：

| 类型 | 数量 | 含义 |
|---|---|---|
| ok | 49 | 该处矢量与影像一致 |
| missing_lane | 78 | 该续未续（你的"二、"） |
| wrong_break | 11 | 连了但不该连 |
| wrong_branch | 10 | 分支/合流形态错（你的"一、"） |
| wrong_count | 2 | 车道数不符 |
| unreadable | 1 | 影像看不清 |

`missing_lane` 占绝对多数，说明这份 Lane 提取的**主要缺陷是漏提/断裂**，
而不是错连——和"很多 Lane 只有 2–3 个顶点、属于短段拼装"的数据特征吻合。


## 已知局限

1. **没有真值，无法算准确率。** 目前只能人工抽查。要评测必须建一个标注集：
   每类问题各 30 个已确认点（含 30 个"本来就该断"的负例），才能算 precision/recall。
2. **置信度不可靠。** 模型给的 0.5–0.7 是自述，和实际正确率不相关，别用来排序。
   更可靠的信号是"同一 Lane 被多个候选重复指出"。
3. **单张图只有 138 m 视野**，约 4 秒的车程。跨图幅的长距离漏提看不出来；
   如果一条线该延伸 200 m，本方案只会告诉你"这里断了"，不会给出完整走向。
4. **纯矢量的 dangle 候选有噪声**：路段拼接、规划中的路口都会产生悬空端点，
   需靠模型 + 人工剔除。

## 怎么跑

```bash
cd /home/liufeng/projects/vlm_projects/vlm_match_sat
python candidates.py                       # 生成候选
python render.py                            # 渲染 crop
python ask.py run --model claude-fable-5-2 --size 1024 --workers 3
python review.py sheet  --model claude-fable-5-2
python review.py apply  --model claude-fable-5-2 --min-conf 0.4

# 交互式查看器（推荐，替代 sheet）
python webexport.py                         # 导出干净底图 + 几何数据
python webexport.py --serve --port 8770     # 起服务，浏览器开 http://127.0.0.1:8770/
```

改判据：`candidates.py` 顶部的 `SEAM_ANG_DEG` / `SEAM_OFF_M` / `MERGE_M`。
改视野：`render.py` 的 `--crop`（1024 ≈ 138 m，1536 ≈ 207 m）。

## 交互式查看器

`viewer/index.html`、`viewer/annotate.js` 是源码（进 git）；底图与几何数据由 `webexport.py` 生成到 `ret/<ver>/viewer/`（`img/*.jpg` + `viewer_data.js`）。

标记全部是客户端 SVG 叠加，可逐层开关：

| 图层 | 用途 | 快捷键 |
|---|---|---|
| 待核实 Lane（红） | 被审判的对象 | `1` |
| 周边 Lane（灰） | 上下文，不用挑它 | `2` |
| Lane 编号 | 对应结论文本里的 L 编号 | `3` |
| 端点（白方块） | 断头位置 | `4` |
| 候选点（黄十字） | 工具算出的位置 | `5` |
| 模型结论圈 | 彩圈，颜色=问题类型 | `6` |
| 模型原始点位 | 淡虚线，显示模型写的坐标偏差 | `7` |
| 两轮一致标记 | 蓝点，打在两轮都判坏的 lane 上 | `8` |
| 矢量模式 | 关掉底图，只看矢量 | `9` |

底图透明度可调（滑块），这样能看清矢量压在影像上的哪个位置。
`←` `→` 切换候选，滚轮缩放，拖拽平移，`f` 适应窗口，`1:1` 原始像素。

### 结论圈为什么要"锚定"

模型给的 `where` 坐标**不可靠**：86 条有问题的结论里，模型自报位置与自己说的那条 Lane
的中位偏差是 **6.6 m，p90 是 26.6 m，最大 41 m**。所以查看器把圈画在"该 Lane 上离模型给的点最近的位置"，
原坐标用淡虚线连出去。看圈的位置时，**以车道为准，不要信模型给的坐标**。

### 人工核对 → 标注集

每条结论下有 `✓ 对` / `✗ 错` 两个按钮，点选后存 localStorage，
右上"导出核对结果"会 POST 到 `/api/mark` 并合并写入 `annotations.json`。
这就是评测集：有了它才能算模型的 precision / recall，否则任何准确率都没有依据。

已知的模型标注瑕疵：C0008_0018 把 `L3` 写成 `L13`，C0004_0002 干脆没写编号（写成"红线-1（最左）"），
这 4 条在查看器里无法锚定到车道，会退化为只有文字结论。
